Recording 是 ink 的核心数据结构

如果只读 Canvas API，你会错过 ink 最重要的抽象。真正连接前端 API 和后端 renderer 的，是 CompactDrawOp、arena、side tables 和 DrawPass。

CompactDrawOp: 小字段 inline，大数据外置

CompactDrawOp 是一个 compact command。它直接保存 type、blend、opacity、flags、color、width；变长或大对象通过 offset/index 指到 arena 或 side tables。 

// include/ink/recording.hpp:73-134
struct CompactDrawOp {
  DrawOp::Type type;
  BlendMode blendMode = BlendMode::SrcOver;
  u8 opacity = 255;
  u8 flags = 0x20;              // cap / join / fillRule / AA / filterQuality
  Color color;
  f32 width;
  u16 shaderIndex = 0xFFFF;
  u16 colorFilterIndex = 0xFFFF;

  union Data {
    struct { Rect rect; } fill;
    struct { Point p1; Point p2; } line;
    struct { u32 offset; u32 count; } polyline;
    struct { Point pos; u32 offset; u32 len; } text;
    struct { u32 pathIndex; f32 miterLimit; } path;
    struct { u32 imageIndex; u32 arenaOffset; } imageRect;
  } data;
};

读代码时看这三件事

  1. 这个 op 的固定字段能不能装下全部参数？
  2. 装不下时，是进 arena，还是进 paths/images/shaders side table？
  3. 最终 dispatch 时，如何把 offset/index 还原成 visitor 参数？
数据类型 存放位置 例子
小标量 直接在 CompactDrawOp color、width、blendMode、opacity、flags
变长 bytes DrawOpArena string、points、matrix、roundRect、rect pair
对象引用 side tables images、paths、shaders、colorFilters

Recorder 如何把 Paint 压进 op

Paint 不是临时参数。Recorder 会把它拆成 compact 字段，并把 shader / colorFilter 保存到 side tables。 

// src/recording.cpp:255-263
void Recorder::applyPaintToOp(CompactDrawOp &op, const Paint &p) {
  op.color = p.color;
  op.blendMode = p.blendMode;
  op.opacity = u8(p.opacity * 255);
  op.width = p.strokeWidth;
  op.flags = (p.cap & 0x3) |
             ((p.join & 0x3) << 2) |
             (p.antiAlias ? 0x20 : 0) |
             ((static_cast<u8>(p.filterQuality) & 0x3) << 6);
  op.shaderIndex = storeShader(p.shader);
  op.colorFilterIndex = storeColorFilter(p.colorFilter);
}

注意

  1. fillRule 没在这里设置，它在 path op 里补到 flags bit 4。
  2. opacity 从 float 变成 0-255 的 u8。
  3. colorFilter 已记录，但当前 CPU/GL path visitor 没真正应用它。
// src/recording.cpp:501-522
void Recorder::fillPath(const Path &path, const Paint &p) {
  CompactDrawOp op{};
  op.type = DrawOp::Type::FillPath;
  applyPaintToOp(op, p);
  Path storedPath = p.pathEffect ? p.pathEffect->filterPath(path) : path;
  u8 fr = (storedPath.fillRule() == FillRule::EvenOdd) ? 1 : 0;
  op.flags = (op.flags & ~0x10) | (fr << 4);
  op.data.path.pathIndex = static_cast<u32>(paths_.size());
  op.data.path.miterLimit = p.miterLimit;
  paths_.push_back(std::move(storedPath));
  ops_.push_back(op);
}

void Recorder::strokePath(const Path &path, const Paint &p) {
  CompactDrawOp op{};
  op.type = DrawOp::Type::StrokePath;
  applyPaintToOp(op, p);
  Path storedPath = p.pathEffect ? p.pathEffect->filterPath(path) : path;
  op.data.path.pathIndex = static_cast<u32>(paths_.size());
  op.data.path.miterLimit = p.miterLimit;
  paths_.push_back(std::move(storedPath));
  ops_.push_back(op);
}

读法

  1. path effect 在记录期应用，不是在 rasterizer 里应用。
  2. fill path 记录 fill rule；stroke path 最终由 renderer 变成 fill geometry。
  3. 路径对象复制进 paths_，op 只存 pathIndex。

Recording 如何 dispatch 到 visitor

Recording 不知道 CPU、GL、Metal。它只知道把 op 解码，然后调用 DrawOpVisitor 的相应方法。 

// src/recording.cpp:196-216
case DrawOp::Type::FillPath: {
  const Path *p = getPath(op.data.path.pathIndex);
  if (p) {
    u8 fillRule = (op.flags >> 4) & 1;
    bool aa = (op.flags >> 5) & 1;
    visitor.visitFillPath(*p, op.color, op.blendMode, op.opacity,
                          fillRule, aa, getShader(op.shaderIndex),
                          getColorFilter(op.colorFilterIndex));
  }
  break;
}
case DrawOp::Type::StrokePath: {
  const Path *p = getPath(op.data.path.pathIndex);
  if (p) {
    u8 capVal = op.flags & 0x3;
    u8 joinVal = (op.flags >> 2) & 0x3;
    bool aa = (op.flags >> 5) & 1;
    visitor.visitStrokePath(*p, op.color, op.width, op.blendMode,
                            op.opacity, capVal, joinVal,
                            op.data.path.miterLimit, aa,
                            getShader(op.shaderIndex),
                            getColorFilter(op.colorFilterIndex));
  }
  break;
}

核心模式

  1. Recording 是 decoder。
  2. Visitor 是 backend-specific executor。
  3. 新增 op 时，必须同步扩展 enum、op storage、recorder、dispatch、visitor、所有 renderer。

DrawPass 排序: 优化和语义的边界

DrawPass 生成的是 sorted op index 列表。它按 clip group、op type、color 排序，目的是减少后端状态切换。但只要有透明 blending，同组内重排就可能影响视觉结果，所以这里是需要主动怀疑的代码。 

// src/draw_pass.cpp:18-68
for (u32 i = 0; i < ops.size(); ++i) {
  const auto &op = ops[i];

  if (op.type == DrawOp::Type::SetClip ||
      op.type == DrawOp::Type::SetClipPath) {
    ++currentClipId;
    sequence = 0;
    keys.push_back(SortKey::make(currentClipId,
                                 DrawOp::Type::FillRect, {}, 0, i));
    sequence = 1;
    continue;
  }
  if (op.type == DrawOp::Type::ClearClip) {
    keys.push_back(SortKey::make(currentClipId,
                                 static_cast<DrawOp::Type>(0xFF),
                                 {0xFF, 0xFF, 0xFF, 0xFF}, 0xFE, i));
    ++currentClipId;
    sequence = 0;
    continue;
  }

  keys.push_back(SortKey::make(currentClipId, op.type,
                               op.color, sequence++, i));
}

std::stable_sort(keys.begin(), keys.end());

要问的问题

  1. clip/transform op 为什么不能和普通 draw op 同等排序？
  2. 同一 clip group 内按 op type 排序是否总是安全？
  3. 如果引入 saveLayer 或复杂 blend mode，这里是否需要更强 ordering model？
学习重点: 这段代码不是“排序算法难”，而是“渲染语义难”。先用测试证明它保留 clip/transform 边界，再讨论 batching 优化。
