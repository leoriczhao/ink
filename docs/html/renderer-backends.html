统一 API 不等于统一 renderer

ink 的用户 API 统一，但后端实现差异很大。学习后端时，不要从 README 的状态表推导能力，要从 Renderer 和 DrawOpVisitor 的实现读起。

Renderer 接口给 Surface 一个统一执行边界

Surface::flush() 只认 Renderer::execute(recording, pass)。至于这个 execute 是 CPU 像素循环、GL draw call，还是 Metal command encoder，是后端自己的事。 

// include/ink/renderer.hpp:25-52
class Renderer {
public:
    virtual void beginFrame(Color clearColor) = 0;
    virtual void endFrame() = 0;
    virtual void execute(const Recording& recording,
                         const DrawPass& pass) = 0;
    virtual void resize(i32 w, i32 h) = 0;
    virtual std::shared_ptr<Image> makeSnapshot() const = 0;
    virtual void setGlyphCache(GlyphCache* cache) { (void)cache; }
};

读法

  1. 先找谁继承 Renderer。
  2. 再找它是否也继承 DrawOpVisitor。
  3. 最后按 visitor 方法对比同一 op 的不同实现。

CPU renderer: visitor 方法直接改 Pixmap

CPU 后端最适合学习图形基础，因为它的结果最终都是写内存中的像素。入口是 src/cpu_renderer.hpp:23。 

// src/cpu_renderer.hpp:23-47
class CpuRenderer : public Renderer, public DrawOpVisitor {
public:
  explicit CpuRenderer(Pixmap *target) : target_(target) {}

  void beginFrame(Color clearColor) override {
    if (target_ && target_->valid()) {
      isBGRA_ = (target_->format() == PixelFormat::BGRA8888);
      target_->clear(clearColor);
    }
    hasClip_ = false;
    hasPathClip_ = false;
    clipMask_.clear();
    currentTransform_ = Matrix::Identity();
  }

  void execute(const Recording &recording,
               const DrawPass &pass) override {
    recording.dispatch(*this, pass);
  }
};

关键点

  1. execute 不循环 op 本身，而是交给 Recording::dispatch。
  2. *this 同时是 renderer 和 visitor。
  3. clip、transform、像素格式都是 renderer 执行期状态。
// src/cpu_renderer.hpp:474-490
void blendPixel(i32 x, i32 y, Color c, BlendMode mode = BlendMode::SrcOver) {
  if (!target_ || !target_->valid())
    return;
  if (x < 0 || x >= target_->width() ||
      y < 0 || y >= target_->height())
    return;
  if (isClipped(x, y))
    return;
  if (hasPathClip_ && clipMaskWidth_ > 0) {
    u8 maskAlpha = clipMask_[y * clipMaskWidth_ + x];
    c.a = static_cast<u8>(c.a * maskAlpha / 255);
    if (c.a == 0)
      return;
  }
  u32 *row = static_cast<u32 *>(target_->rowAddr(y));
  u32 &pixel = row[x];
  Color dst = decodePixel(pixel);
  pixel = encodePixel(blendColors(c, dst, mode));
}

这里是像素 contract

  1. 边界检查。
  2. clip / path clip。
  3. decode 目标像素。
  4. blend。
  5. encode 回目标格式。

GL backend: GpuContext 是 public wrapper，GLImpl 是内部实现

GpuContext 也实现 Renderer，但它只是把调用转给 GpuImpl。GL 后端真正的执行代码在 GLImpl。 

// src/gpu/gpu_context.cpp:17-31
void GpuContext::beginFrame(Color clearColor) {
  if (impl_) impl_->beginFrame(clearColor);
}

void GpuContext::execute(const Recording& r, const DrawPass& p) {
  if (impl_) impl_->execute(r, p);
}

void GpuContext::readPixels(void* dst, i32 x, i32 y, i32 w, i32 h) const {
  if (impl_) impl_->readPixels(dst, x, y, w, h);
}

读法

  1. include/ink/gpu/gpu_context.hpp 是 public API。
  2. src/gpu_impl.hpp 是 internal backend interface。
  3. src/gpu/gl/gl_context.cpp 里有具体 GL 实现。
// src/gpu/gl/gl_context.cpp:297-317, 412-416
class GLImpl : public GpuImpl,
               public GLInterop,
               public DrawOpVisitor {
public:
  GLFramebuffer framebuffer_;
  GLShaderProgram colorProgram_;
  GLShaderProgram texProgram_;
  GLVertexBuffer<GLColorVertex> colorBuffer_;
  GLVertexBuffer<GLTexVertex> texBuffer_;
  GLTextureCache textureCache_;
  Matrix currentTransform_;
  std::vector<GLColorVertex> colorVerts_;
  std::vector<GLTexVertex> texVerts_;

  void execute(const Recording &recording,
               const DrawPass &pass) override {
    currentRecording_ = &recording;
    recording.dispatch(*this, pass);
    flushColorBatch();
    currentRecording_ = nullptr;
  }
};

关键点

  1. GL 也用 visitor 分发。
  2. 普通颜色绘制先 push vertex，再 batch flush。
  3. texture、framebuffer、stencil 都是 GLImpl 的执行期资源。

同一 op 的后端差异

下面这张表比“支持 CPU/GL/Metal”这种总览更有学习价值。你要养成按 op 对比后端的习惯。

DrawOp CPU renderer GL renderer 学习重点
FillRect mapRect 后逐像素 fill + blend。 pushQuad 到 color vertex batch。 CPU 是 pixel loop，GL 是 vertex geometry。
Line 简单 Bresenham-like loop 加宽度覆盖。 把线段扩成 quad 加入 batch。 线宽在不同后端不是同一个算法。
FillPath PathRasterizer scanline coverage。 实心 path stencil-cover；带 shader 时 CPU raster 到 texture。 性能和质量讨论必须说清路径。
StrokePath StrokeEngine::strokePath 后再 fill。 也先 stroke-to-fill，再 stencil-cover 或 texture。 stroke 算法共享，但执行方式不同。
DrawImage 只处理 CPU-backed image；GPU-only image 直接返回。 CPU image 上传并缓存，GPU image 直接取 texture handle。 跨后端 image interop 是真实限制。
ClipPath 生成 alpha mask，后续像素 alpha 乘 mask。 用 stencil bits 表达当前 clip。 同一语义，两套资源模型。

GL path 的两条路径

当前 GL path 不是单一实现。没有 shader 的 path 走 stencil-cover；带 shader 的 path 走 CPU raster 到临时 texture。

实心 path: stencil then cover

// src/gpu/gl/gl_context.cpp:817-844
clearStencilBits(kPathStencilMask);
stencilPathBits(contours, fillRule, clipStencilActive_);

Rect bounds = boundsForContours(contours);
glStencilMask(0x00);
glStencilFunc(GL_NOTEQUAL, 0, kPathStencilMask);
drawSolidRectNoTransform(bounds, color);

clearStencilBits(kPathStencilMask);
restoreClipStencilState();

shader path: CPU raster texture

// src/gpu/gl/gl_context.cpp:847-869
Pixmap pm = Pixmap::Alloc(PixmapInfo::MakeRGBA(w, h));
pm.clear({0, 0, 0, 0});

PathRasterizer rasterizer;
rasterizer.addPath(path, currentTransform_);
rasterizer.rasterize(&pm, fullBounds, color,
                     BlendMode::Src, opacity,
                     antiAlias, fillRule, shader, false);

glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA8,
             w, h, 0, GL_RGBA, GL_UNSIGNED_BYTE, pm.addr());
不要过度宣称: “GL 支持 path”不等于“所有 path 都原生 GPU tessellation”。当前源码里仍有 CPU raster fallback。
