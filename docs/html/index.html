给 C++ 开发者的 ink 源码学习导览

这份导览不再介绍“ink 是什么项目”。它的目标是带你读懂这套 2D 渲染库的代码：对象边界、命令记录、排序、visitor 分发、路径栅格化、CPU/GL 后端差异。

先抓住代码主线

你已经熟悉 C++，所以最短路径不是补图形学名词，而是先把它当作一个 record-then-execute 的系统。下面这条链路就是整库的骨架。

Surface 拥有 Canvas、Device、Renderer，定义帧生命周期。
Canvas 用户侧 facade，维护 clip / transform / save stack。
Recorder 把 draw 调用压成 CompactDrawOp 和 side tables。
DrawPass 按 clip/transform group、op type、color 生成执行顺序。
Renderer 通过 DrawOpVisitor 真正改像素或提交 GPU draw。
关键校正: 不要把 canvas->fillRect(...) 理解成“马上写像素”。在 ink 里，它先变成记录命令；像素变化发生在 Surface::flush() 之后。

每个章节都按“读哪些文件 -> 核心代码片段 -> 验证任务 -> 容易误解的点”组织。按顺序读一遍，基本就能开始给 ink 写小功能或修测试。

你读代码时要一直问的 5 个问题

1. 这个函数是在记录，还是在执行？

Canvas 和 Device 多数时候只是记录。CpuRenderer 和 GLImpl 的 visitor 才执行。

2. 状态在哪里保存？

Canvas 保存当前 clip/transform；Recording 保存 SetClip/SetTransform op；Renderer 也保存执行期状态。

3. 数据是 inline 还是 side table？

CompactDrawOp 存小字段，大对象如 strings、paths、images、shaders 存在 arena 或 side tables。

4. 排序有没有改变语义？

DrawPass 会重排同组绘制命令。clip/transform 是边界，但同组内的重排要小心 blending 语义。

5. CPU 和 GPU 走的是同一算法吗？

不是。CPU path 用 scanline coverage；GL 实心 path 用 stencil-cover；带 shader 的 GL path 当前走临时 CPU raster texture。

6. 文档与源码冲突时信谁？

优先信源码和构建脚本。例如 backends 文档说 GL 默认开启，但 CMakeLists.txt 里 INK_ENABLE_GL 默认是 OFF。
