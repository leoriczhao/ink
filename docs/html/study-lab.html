用 9 个小实验学会 ink

读源码如果没有可验证目标，很容易变成“看过”。下面的任务都很小，每个任务都对应明确文件、要观察的现象和验证命令。

准备工作

构建测试

cmake -B build -DINK_BUILD_TESTS=ON
cmake --build build
ctest --test-dir build --output-on-failure

推荐读法

  1. 先打开本页任务。
  2. 按行号读源码，不急着改。
  3. 写一个很小的测试或临时日志。
  4. 跑指定测试，确认你的模型对不对。
工作区提示: 当前仓库已有未提交改动。做实验时不要随手格式化无关文件，也不要重置已有改动。

阶段 A: 建立调用链模型

实验 1: 证明 draw 不立即写像素

目标文件: tests/test_surface.cpp 或新建一个 focused test。

  • 创建 raster surface。
  • beginFrame 后画一个 red rect。
  • 在 endFrame 后、flush 前检查中心像素。
  • 再 flush，检查像素变红。

实验 2: 打印 Recording ops

目标文件: tests/test_recording.cpp。

  • 用 Recorder 手工记录 fillRect、setClip、drawLine。
  • 检查 ops().size() 和每个 DrawOp::Type。
  • 确认 string/path/image 不直接塞进 op。

实验 3: 追踪 save/restore

目标文件: tests/test_canvas.cpp 或 tests/test_transform.cpp。

  • 构造 translate + save + clip + restore。
  • 检查 recording 里是否出现 ClearTransform / SetTransform / ClearClip。
  • 解释为什么 restore 不是单纯 pop C++ stack。

阶段 B: 建立命令排序模型

实验 4: 画出 DrawPass sorted indices

目标文件: tests/test_draw_pass.cpp。

  • 构造 6 个 op: fill、line、clip、fill、clearClip、line。
  • 打印原始 index 与 sorted index。
  • 解释哪些移动是 batching，哪些边界不能跨。

实验 5: 设计一个 alpha 排序反例

目标文件: tests/test_draw_pass.cpp 或 tests/test_blend.cpp。

  • 两个半透明 rect，颜色不同，位置重叠。
  • 交换绘制顺序，比较像素。
  • 思考 DrawPass 同组内按 type/color 排序是否永远安全。

实验 6: 新增一个最小 DrawOp 的清单

不一定真改，实现前先列改动面。

  • enum。
  • CompactDrawOp::Data。
  • Recorder 方法。
  • Recording::dispatchOp。
  • DrawOpVisitor。
  • CPU/GL/Metal visitor。
  • 测试。

阶段 C: 建立 Path 到像素模型

实验 7: 观察 fill rule

目标文件: tests/test_path.cpp。

  • 构造两个同心 rect 或 circle。
  • 默认 Winding 下检查中心点。
  • EvenOdd 下再检查中心点。
  • 把测试和 fillScanline 的 winding 变量对应起来。

实验 8: 让 rasterizer 输出交点

临时调试，不建议提交日志。

  • 给一个三角形 path。
  • 在 fillScanline 里打印某一行的 x intersections。
  • 手算这条 scanline 应该填充的 x 范围。

实验 9: 验证 stroke-to-fill

目标文件: tests/test_path.cpp。

  • 调用 StrokeEngine::strokePath 生成 stroked path。
  • 检查输出 path 不为空。
  • 尝试 Butt/Round/Square cap，看 points/verbs 数量变化。

一个适合上手的小修复: 接通 CPU path ColorFilter

这个修复足够小，又能迫使你理解 Paint -> Recording -> Dispatch -> Renderer 的完整链路。

Paint paint.colorFilter 已存在。
Recording colorFilterIndex 已记录。
Dispatch visitor 参数已经带 ColorFilter*。
CpuRenderer 当前 path visitor 忽略了这个参数。
Test 用 matrix filter 验证颜色被改变。 
// 当前事实: src/cpu_renderer.hpp:303-305
void visitFillPath(const Path &path, Color color, BlendMode blend,
                   u8 opacity, u8 fillRule, bool antiAlias,
                   const Shader *shader,
                   const ColorFilter *) override {
  ...
}

实现方向

  1. 让 PathRasterizer::rasterize 接收可选 ColorFilter*。
  2. 在 shader/color 产出后、coverage alpha 应用前或后，明确选择过滤顺序。
  3. 为纯 color fill 和 shader fill 各加一个测试。
  4. 确认 GL path texture fallback 是否也要传递 filter。
先定语义: ColorFilter 应该作用在 shader 结果之后、blend 之前。这是一个语义选择，不是机械加函数调用。

读源码顺序清单

顺序 文件 读完应该能回答

7 src/cpu_renderer.hpp visitor 方法如何把 op 执行为 CPU 像素？
8 src/gpu/gl/gl_context.cpp, src/gpu/gl/gl_resources.hpp 同一个 op 如何变成 GL state、vertex batch、stencil、texture？
